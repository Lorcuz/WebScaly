# Compatibility validation

0.4.0 changes the rendering pipeline, the overlay and the interface; access control is unchanged. The controlled browser checks below were re-run on 0.4.0 (native video, JW-style, Video.js, Plyr, HLS, DASH, frames, shadow DOM, fallbacks, compatibility player). On 21 October 2026 the anonymous live check was repeated on 0.4.0 for YouTube, Vimeo, Twitch and Dailymotion with the same outcomes as below: Dailymotion enhanced sustained playback at native rate with WebGPU (512×288 → 1600×900, about 30 fps) and its toolbar and comparison drag passed; YouTube engaged the WebGPU renderer on decoded frames but paused anonymous playback; Vimeo and Twitch produced no decoded frames in the test browser, which most likely lacks the proprietary codecs those sites serve. AnimeWorld and AnimeUnity/Vixcloud were not repeated for 0.4.0.

Plain `http://` websites are not secure contexts, so browsers do not offer WebGPU there; WebScaly uses its WebGL Spatial Detail fallback on such pages. A browser test covers this case.

Checks completed on 12 October 2026. Results apply to the tested pages and local browser; they do not certify every page, Chrome version or physical GPU. Anonymous live checks use an isolated profile with explicit test-only grants. The shipped manifest grants no websites by default.

No live website in this session was qualified through the compatibility player. The compatibility player separately passed a controlled Chrome tab-sharing, crop and cleanup test. It remains an explicit fallback to try when browser origin rules prevent direct access; protected content can remain black.

Controlled browser checks passed for native HTML5 video, a JW/Vixcloud-style container, actual Video.js and Plyr, and locally generated HLS/DASH streams played by HLS.js and dash.js. These checks cover pause, seek, container fullscreen, source replacement, cleanup, late open Shadow DOM, inherited-origin frames, isolated controls, comparison dragging, and parent/frame permission revocation. A pixel regression verifies that native JW-style controls and captions remain visible while enhancement is active.

All three enhancement algorithms produced nontrivial opaque output on the local WebGPU device. Native 24/30/60 FPS inputs were exercised. Missing WebGPU/context support, WebGL 1, optional GPU features, low reported texture limits, neural initialization failure, blocked UI frames and device loss were exercised separately. Capability overrides are simulations; device loss used an actual device destruction. They are not physical AMD or Intel qualification.

The installed Chrome approval flow Add → Allow was manually confirmed to complete without reopening the popup. Automated worker-model tests cover denial, duplicate requests, late grants, cancellation, worker recovery and overlapping removal. Native denial and restart recovery still require a separate installed-profile release check. Chrome 121 is the audited API/build target; this run did not use a physical Chrome 121 installation.

Protected media, browser pixel-access restrictions, unapproved parent/player origins, closed Shadow DOM and native video-element fullscreen are explicit limits. Native fullscreen retains native video; container fullscreen can retain enhancement. If a site blocks the bundled interactive frame, use the popup.
